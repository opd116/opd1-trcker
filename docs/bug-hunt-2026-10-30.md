## Area 1 — Skins / owned collection (confirmed, PR #5)

**Hypothesis/area:** "skins sometimes fail to appear" on the Skins screen.

**Finding SKINS-1 (confirmed, regression test fails on baseline).**
- Trigger: first `collection` invoke on an account with no stored copy; Riot's
  `/store/v1/entitlements/{self}/skin_levels` call meets one transient failure (5xx/timeout), or a 429 whose
  hold is longer than the in-call wait.
- Observed (baseline 0428c52): `src-tauri/src/v2/collection.rs` recorded the process-wide `LAST_ASK`
  unconditionally after the Riot call, before examining its result. The failure therefore counted as the
  ten-minute refresh. With no stored copy the command returned `Ok(None)`, so the Skins screen showed its
  definitive "No collection yet — open this page while VALORANT is running" empty state **while the game was
  running**, and every 60 s UI retry returned the same `None` for up to ten minutes.
- Expected: a failed ask is retried on the screen's own retry; `Ok(None)` only for the legitimate
  "no ask attempted" states (no session, game closed/stale session, no self puuid). A failed ask with a
  stored copy keeps showing the stored copy.
- Root cause and source evidence: `src-tauri/src/v2/collection.rs`, `refresh_if_due` (LAST_ASK write before
  the answer branch) and `collection` (no distinction between "never fetched" and "fetch failed").
- Fix: only a **stored** answer records `LAST_ASK`; a failed/held ask with nothing stored is `Err`
  ("skins unavailable") so the screen stays in its retry state. `Ok(None)` preserved and pinned for the
  no-ask cases. Round 4 closed the account-switch residual in the same command: after the Riot await it
  re-reads `live.self_puuid`; if the account changed while the call was in flight it returns
  `Err("skins unavailable")` instead of the previous account's stored copy, so the screen keeps its retry/
  skeleton state (never the definitive "No collection yet" empty state) and asks again for the current
  account — the UI side of that re-ask is PR #8's account handler, so #5 and #8 are reviewed together in the
  recommended order. (The adversarial reviewer of the combined set flagged that an earlier `Ok(None)` from
  this guard contradicted the documented `None` contract; the follow-up commit made it `Err`.)
- Reproduction: `src-tauri/src/v2/collection.rs` tests, mock Riot: 500 then 200; two asks must reach the
  mock and the second must store the level. Baseline: one request, no stored copy. Baseline evidence
  captured by the implementer before the fix. Round 4 adds a superseded-call test: it waits until the mock
  has received the entitlements request (no wall-clock sleep), switches `self_puuid` to B while the mock
  holds the answer, and asserts the in-flight call is `Err("skins unavailable")` (never A's levels), while a
  following call for B serves B's own copy; with `Ok(None)`/no guard the test fails for the right reason.
- PR: [#5](https://github.com/opd116/opd1-trcker/pull/5), branch `fix/skins-collection`, final head
  `da0404c718cbe125893d0527cfecf6ebe72590f3` (after the reviewer follow-up, the round-4 account guard and the
  reviewer nit that made it `Err`; both CI runs green: PR 41097187970, push 41097180789).
- Remaining uncertainty: verified against a mock, not the live Riot store endpoint; real-client confirmation
  that a failed first attempt shows the retry state and recovers within a minute is still needed.
- **Negative result (round 5, bounded investigation; no bug, no change):** catalog/identifier mismatch edges
  cannot make owned skins disappear wrongly. With local wiremock valorant-api answers: an owned level absent
  from the catalog (new skin/API lag) is skipped gracefully (`Ok`, other items kept; all-unknown → `Ok` with
  empty items and `fetchedMs` kept, no `Err`/panic/blank); partial rows degrade locally (a nameless weapon
  drops with its skins, a skin with `levels: null`/`[]`/a level without a uuid drops individually, and a
  malformed `chromas` shape is irrelevant because the collection join never reads chromas; the chroma path is
  loadout-only); malformed/partial catalog JSON is bounded (a wrong-typed body fails the decode but an older
  catalog is served and the retry window prevents re-downloads, `data: []`/no `data` never writes an empty
  catalog file, a truncated cache file is ignored and rebuilt); empty/duplicate owned levels are valid (empty
  → legitimate "No skins owned yet.", duplicates dedup by skin uuid); a catalog build failure is `Err` →
  the Skins screen's retry state, not the `null` empty state. Only theoretical residual: if *every* owned
  level were unknown to a stale older catalog the join is `Ok(empty)` until the next retry-window ask (exotic
  timing; fixing it needs new UI text/state, R191). Six new tests were written in a scratch worktree and all
  passed; the worktree/branch were removed, nothing pushed.

## Area 2 — Live player names (confirmed, PR #6)

**Hypothesis/area:** "player names sometimes disappear and reappear".

**Finding NAMES-1 (confirmed, regression test fails on baseline).**
- Trigger: a reset stage transition (dodge Agent Select back to Lobby; also a match end for a stale slot)
  while a roster player's stored slot bundle predates the name-service answer (e.g. the names step stored the
  name before that player's rank phase reloaded their bundle).
- Observed (baseline 0428c52): `poll::change_stage`'s reset path calls `LiveModel::forget_synced()`, which
  clears `known_names` (the stage's live name answers). `apply_roster` only reads DB bundles for new players,
  so a carried slot keeps the stale bundle whose row has no name; `card_for` then has neither the live answer
  nor a stored name and publishes `Field::Loading`. The card falls back to the loading skeleton and the name
  reappears only after the re-asked name-service answer.
- Expected: a name the DB already stores (and that was on screen a moment earlier) is never replaced by a
  loading skeleton by a stage transition.
- Root cause and source evidence: `src-tauri/src/poll.rs` (`change_stage` reset → `forget_synced`),
  `LiveModel::apply_roster` (carried slots keep their `Slot.db`), `card_for` name precedence.
- Fix (reviewed, final): a `reload_roster_rows` flag set on reset transitions makes `apply_roster` do
  one keyed `players`-row read per carried roster player (not the whole bundle) and restore a slot's row
  only when the slot has no name, so a concurrent newer row is never overwritten; the flag is kept when a
  read fails and cleared wherever every slot is replaced anyway. Name-service is still re-asked after the
  reset, so the rename rule is intact. Round 5 extended the same reload with a second keyed read,
  `Repo::known_name(me, puuid)`, and applies it to the carried slot's `db.remembered` only when the DB has
  one (never blanking it, skipped for self): a hidden player's card reads its name only from
  `db.remembered`, and a match row naming that player can be stored while the slot is carried (another
  roster player's matches phase, the post-match store, or the backfill all `Repo::upsert_match` without
  touching other slots), so without the second read the card kept `HiddenPlayer`/the older remembered name
  across a dodge or match end even though the DB knew a name. Cost: one extra indexed SELECT per carried
  player on reset transitions only; DB-only, no request, hidden-name style/source and privacy rules
  unchanged.
- Reproduction: `src-tauri/src/pipeline_tests/name_stability.rs` — app opened during Agent Select, name
  published, OTHER's rank phase held by a long-delayed 500 so their bundle is provably stale, then presence
  flips to MENUS (dodge). Baseline publishes `name: Loading`; fix keeps the stored name. Round 5 adds a
  hidden-player variant (`a_hidden_player_carried_through_a_reset_shows_the_remembered_name_the_db_now_knows`):
  HIDDEN is the user's incognito party member with its rank phase held; a match ME and HIDDEN played is
  stored with the real sync write after the bundle read (DB `known_name` = `Remembered{SecretName#HID,
  ownMatch}`), then a dodge; every published Lobby state that shows HIDDEN must carry exactly that remembered
  name/source/from_start_ms (never `HiddenPlayer`/`HiddenAgent`), a second reset (Lobby → Agent Select →
  Lobby) keeps it, and no name-service request body may contain HIDDEN's puuid (privacy). All four tests run
  in ~0.03 s with no wall-clock waits.
- PR: [#6](https://github.com/opd116/opd1-trcker/pull/6), branch `fix/names-live`, final head
  `ce003573a1c7a2693d5d0b8f901c2e690e966f83`. Round 3 added the coverage the independent reviewer flagged:
  a match-end reset test and a failed-roster-fetch/retry case (documented to pass on baseline because
  `show_self_only` replaces every slot, so the carried-row defect cannot survive that path). Baseline matrix
  (production `poll.rs` restored to `0428c52`, tests unchanged): dodge FAIL (`Loading` vs DB `Other#OTH`),
  match-end FAIL (same), hidden-remembered FAIL (`HiddenPlayer` vs DB `Remembered{SecretName…}`), failed-fetch
  pass by design. Round 6 came after an independent review of the round-5 commits (`f943f37`): no blockers;
  nits (a recency guard for the remembered overwrite, overwrite-branch coverage, module docs) were fixed in
  `1956f0e`/`1e7ded0`. A CI-only flake in the overwrite-branch assertion (a loaded runner let an aborted
  worker's publish land after the marker; suite ran 62 s instead of ~13 s) was fixed test-only in `ce00357`
  (worker stopped before the toggles; the assertion now requires the *last* Lobby state to carry the newer
  remembered name and no state to blank it; verified 25/25 focused runs and 10/10 full-module runs under 8 CPU
  load jobs). Both CI runs green on the final head: PR 41117948206, push 41117941184.

**Finding NAMES-2 (round 6; confirmed with a real-Poller test, fixed in PR #6).**
- Trigger: while a hidden player's card is on screen, a match that names them is stored by
  `sync::store_details` (the worker's matches phase for another roster player, the backfill, or opening Match
  Details). The worker syncs roster players in display order, so a hidden ally can already be synced when a
  later player's matches phase stores a match naming them.
- Observed: no slot refresh followed the store, so the card kept `HiddenPlayer`/an older remembered name until
  that player's own sync publish, a names fill, or the next stage reset — a user-visible "name appears late"
  window. R145 says any name the DB knows is shown during live stages.
- Root cause: remembered data reaches a slot only at install, that player's own publish, a fill, or the reset
  reread; `store_details` writes match rows but never refreshed other slots.
- Fix (round 6, final): after the rows are stored, `store_details` collects the match's named, non-self
  players currently carried as incognito slots and reloads just those slots from the DB (`reload_slots`), only
  when the stored match can be a newer source (the slot has no remembered name, or the match start is at/after
  the slot's; ties reload, the DB read is authoritative) — documented. DB-only, no request; the live match
  itself cannot be stored while live, so there is no live-stage leak; hidden style/source and privacy
  unchanged. Cost: one roster scan O(players×slots) per stored match plus one bundle read/build per matching
  carried hidden player, only when newer.
- Reproduction: real-Poller test `a_match_stored_while_a_hidden_player_is_carried_refreshes_their_remembered_name`
  (hidden party member carried and already synced; a match stored through the real `sync::store_details` names
  them; the card shows the newer remembered name at once; no name-service body contains the hidden puuid),
  plus negative tests `an_older_stored_match_does_not_refresh_a_newer_remembered_name` and
  `a_stored_match_naming_a_visible_player_publishes_nothing`. Reviewer: approve-with-nits, no blockers; nits
  (reload only newer stores, module doc, negative coverage, sequential-read comment) fixed in `1e7ded0`.
- Remaining uncertainty / coverage gap: the reset-transition and cross-player store windows are closed; an
  older stored match cannot improve the shown name (guarded), and a concurrent older reload could still
  overwrite until the next refresh (pre-existing, documented). Mocks only; real-client observation of a
  dodge/match end with a newly known hidden name is still needed.

## Area 4 — Riot account switch (confirmed, PR #8)

**Hypothesis/area:** switching accounts in a Riot client that stays open is a supported flow; after the switch the
UI must not keep serving the previous account's data.

**Finding ACCOUNT-1 (confirmed, browser regression test fails on baseline).**
- Trigger: the Riot client switches accounts while the app is open (its session drops and reconnects; Rust replaces
  the whole live state and re-pushes My Stats when the switch is noticed). The self card's PUUID changes.
- Observed (baseline 0428c52): the UI had no reaction to the new self card, so every open, account-scoped surface
  kept the previous account's data indefinitely: the History list (rows, and the module-level `historyCache`, which
  also drew the old rows on a remount before the refresh answered; an in-flight old page could land afterwards),
  the Skins collection (including the total VP), Saved's records with/against and LAST SEEN (computed for
  `self_puuid` when `saved_players` was asked), and the profile drawer / scoreboard, whose "Your result",
  encounters and own row are relative to the previous user.
- Expected: an open page either shows the new account's data or a neutral loading state; user-relative overlays
  close rather than showing the old account's numbers.
- Root cause and source evidence: no account-change signal in the UI (`ui/src/lib/stores.ts` only stored `live`);
  refresh triggers were mount/queue switch/stage change/match end only (`HistoryList`, `Saved`, `Skins`); the
  History module cache (`ui/src/components/history/cache.ts`) was not account-scoped; in-flight guards (`gen`,
  `alive`) were only bumped by those same non-account triggers.
- Fix (reviewed; two follow-up rounds hardened it): one UI account signal in `ui/src/lib/stores.ts` —
  `selfId` prefers the live self card, then the live state's `selfPuuid` (the session's own account, which
  Rust now carries on the wire as an optional field, serialized only when known), then the last account a
  live state named, and falls back to the My Stats snapshot's puuid only before any live signal, so a stale
  snapshot cannot move the account back; `onAccountChange(fn)` fires only when two known accounts differ in
  turn (never on startup/first account, a dropped connection, an empty live state or Closed↔Menus; a
  persisted-account snapshot followed by the connected account at boot is a real change and may fire once).
  On a switch: History clears its shown page and its module cache — the cache starts an account epoch and
  rejects any page asked for under an older epoch, so an answer from a list instance the switch unmounted
  cannot repopulate it — and refreshes with the new generation; Skins bumps its generation synchronously,
  clears its collection and re-asks; Saved clears and reloads; the open tooltip, profile drawer and scoreboard
  close (`hideTip()`, then `backFromMatch({ reopenProfile: false })`) because they cannot be corrected in
  place, leaving the refreshed screen under them. Rust clears the previous session's roster slots in the same
  critical section that replaces `self_puuid`, so no old account's card can be published under the new puuid.
  The wire field keeps old payloads valid (absent when unknown, never `null`); no schema, route or dependency
  change. Round 4 closed the My Stats residual: a central `myStatsForSelf` derived store (snapshot only while
  `mystats.puuid === selfId`, preserving each consumer's tri-state meaning) is now used by every user-relative
  My Stats consumer — Competitive, NavRail rank, WaitingView, the profile drawer's Net RR/games, the recap and
  the scoreboard's "YOUR RR" — so a stale snapshot cannot draw the previous account's numbers during the
  pre-push window.
- Reproduction: `ui/tests/account-switch.spec.ts` — a fake-Tauri harness with account-aware commands; boot as
  account A, open the surface, flip the fake account and emit the new account's `live` state at the **same
  stage** (asserted, so the pre-existing stage-change refresh cannot mask the bug), then assert A's data is
  gone. Eleven cases now: History, an in-flight A page released after the switch, Skins, Saved, drawer,
  scoreboard, a scoreboard opened from the drawer whose drawer must not reopen, three "VALORANT closed,
  never-seen account, only `selfPuuid` names it" cases, and "switch with My Stats still A's". The last one
  (rounds 4–5) asserts the stale snapshot is dropped, Competitive leaves its skeleton for the `—` frames
  (round 5's reset + one DB-only ask, since Rust cannot emit a null `mystats` event), exactly one extra
  `my_stats` ask happens for the switch (not one per screen), and a later B `mystats` push fills "222 / 100
  RR"/NavRail. On baseline the seven mid-match cases fail with A's values (e.g. History expected B's row, got
  none; Skins expected "2,550", got "875"; Saved expected "9 games", got "3 games"; drawer/board still open),
  the three closed cases fail on the fixed-before-the-wire-change sources exactly 3/3, the stale-My-Stats case
  fails on the pre-guard sources, and the round-5 reset/ask fails with "expected 2 my_stats asks, received 1"
  when only the handler reset is reverted. With the final fix all eleven pass; unit tests pin the signal,
  guard, reset and late-answer semantics (15 new UI tests in total, 633 Vitest).
- PR: [#8](https://github.com/opd116/opd1-trcker/pull/8), branch `fix/account-switch-data`, final head
  `26432848c3bbdeb7b414c644b3cfd6c807f4f0dc` (after the reviewers' follow-ups, the round-4 My Stats guard, the
  round-5 reset/re-ask, the round-6 nits and the round-7 cross-account preservation test; both CI runs green:
  PR 41132928691, push 41132921808).
- **Cross-account preservation coverage (round 7, user-requested, test-only).** The user requires that
  account-specific screens/stats/history/collection follow the current Riot account while locally learned
  player names stay shared across Riot accounts in the installation (keyed by PUUID). `KNOWN_NAME_SQL` already
  searches every stored match/`players` row by the other PUUID with no account filter (source `otherMatch`
  when the current user was not in that match), so no production change was needed. New real-Poller test
  `names_learned_on_one_account_are_shared_but_account_data_follows_the_session`: A's stored match names X,

  through X's PUUID; no name-service PUT body on either mock server contains X (and none was needed at all);
  `known_name` returns `OwnMatch` for A and `OtherMatch` for B; B's history/My Stats list only B's match and
  B's PlayerDetails for X has 0 encounters while A's has 1 on A's match. The same scenario passes on
  `origin/main` with only the `selfPuuid` assertion adjusted (main has no wire field), proving the behaviour
  predates the account-switch PR and is now pinned. Test-only; PR #8 head `2643284`.
- Remaining uncertainty / residual: closed within the set — `collection()`'s in-flight old-account copy is
  fixed in PR #5's round-4 guard, the stale My Stats window is guarded in round 4, and the "new account not

## Area 5 — CI test flake (confirmed and fixed, PR #9)

**Hypothesis/area:** the one full local Rust run in round 1 that exited 1 with a green-looking tail, and CI
reliability generally.

**Finding FLAKE-1 (confirmed, reproduced deterministically).**
- Trigger: a `Build` push run for the docs head `271e047` failed its `checks` job in **Test Rust crates**
  (`pipeline_tests::status::matchmaking_in_the_lobby_shows_the_queue_timer_and_ends_the_recap`, `status.rs:584`,
  `assertion failed: since >= before`) while the same commit's `pull_request` run passed; the suite took 60.81 s
  instead of the usual ~13 s (two CI jobs shared the runner).
- Root cause: the test captured `before = now_ms()` **after** the tick that first records the queue timer's
  start, then asserted the later "no entry time" start (`since`, which is that earlier tick's timestamp) is
  `>= before`. That only holds while the few status reads between the tick and the capture finish inside the
  same millisecond. The app behaviour is correct — a further tick keeps the same start, which the test also
