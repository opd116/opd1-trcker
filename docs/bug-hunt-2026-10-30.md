## Area 1 — Skins / owned collection (confirmed, PR #5)

**Hypothesis/area:** "skins sometimes fail to appear" on the Skins screen.

**Finding SKINS-1 (confirmed, regression test fails on baseline).**
- Trigger: first `collection` invoke on an account with no stored copy; Riot's
  `/store/v1/entitlements/{self}/skin_levels` call meets one transient failure (5xx/timeout), or a 429 whose
  hold is longer than the in-call wait.
- Observed (baseline 0428c52): `src-tauri/src/v2/collection.rs` recorded the process-wide `LAST_ASK`
  unconditionally after the Riot call, before examining its result. The failure therefore counted as the
  ten-minute refresh. With no stored copy the command returned `Ok(None)`, so the Skins screen showed its
  definitive "No collection yet — open this page while VALORANT is running" empty state **while the game was
  running**, and every 60 s UI retry returned the same `None` for up to ten minutes.
- Expected: a failed ask is retried on the screen's own retry; `Ok(None)` only for the legitimate
  "no ask attempted" states (no session, game closed/stale session, no self puuid). A failed ask with a
  stored copy keeps showing the stored copy.
- Root cause and source evidence: `src-tauri/src/v2/collection.rs`, `refresh_if_due` (LAST_ASK write before
  the answer branch) and `collection` (no distinction between "never fetched" and "fetch failed").
- Fix: only a **stored** answer records `LAST_ASK`; a failed/held ask with nothing stored is `Err`
  ("skins unavailable") so the screen stays in its retry state. `Ok(None)` preserved and pinned for the
  no-ask cases. Round 4 closed the account-switch residual in the same command: after the Riot await it
  re-reads `live.self_puuid`; if the account changed while the call was in flight it returns `Ok(None)`
  instead of the previous account's stored copy (the Skins screen, the command's only caller, asks again for
  the current account and drops stale answers — the UI side of that re-ask is PR #8's account handler, so #5
  and #8 are reviewed together in the recommended order).
- Reproduction: `src-tauri/src/v2/collection.rs` tests, mock Riot: 500 then 200; two asks must reach the
  mock and the second must store the level. Baseline: one request, no stored copy. Baseline evidence
  captured by the implementer before the fix. Round 4 adds a delayed-answer test: a call starts for account
  A, `self_puuid` switches to B while the mock holds the answer, and the result must be `Ok(None)` (never
  A's levels), while a following call for B serves B's own copy; without the guard the test fails with
  `Ok(Some(Collection { items: [Reaver], fetched_ms: 5 }))` for the switched account.
- PR: [#5](https://github.com/opd116/opd1-trcker/pull/5), branch `fix/skins-collection`, final head
  `361633f1d5ffecc9c7c16023cc5c9c4951a3330e` (after the reviewer follow-up and the round-4 account guard;
  both CI runs green: push 41092472077, PR 41092477512).
- Remaining uncertainty: verified against a mock, not the live Riot store endpoint; real-client confirmation
  that a failed first attempt shows the retry state and recovers within a minute is still needed.

## Area 2 — Live player names (confirmed, PR #6)

**Hypothesis/area:** "player names sometimes disappear and reappear".

**Finding NAMES-1 (confirmed, regression test fails on baseline).**
- Trigger: a reset stage transition (dodge Agent Select back to Lobby; also a match end for a stale slot)
  while a roster player's stored slot bundle predates the name-service answer (e.g. the names step stored the
  name before that player's rank phase reloaded their bundle).
- Observed (baseline 0428c52): `poll::change_stage`'s reset path calls `LiveModel::forget_synced()`, which
  clears `known_names` (the stage's live name answers). `apply_roster` only reads DB bundles for new players,
  so a carried slot keeps the stale bundle whose row has no name; `card_for` then has neither the live answer
  nor a stored name and publishes `Field::Loading`. The card falls back to the loading skeleton and the name
  reappears only after the re-asked name-service answer.
- Expected: a name the DB already stores (and that was on screen a moment earlier) is never replaced by a
  loading skeleton by a stage transition.
- Root cause and source evidence: `src-tauri/src/poll.rs` (`change_stage` reset → `forget_synced`),
  `LiveModel::apply_roster` (carried slots keep their `Slot.db`), `card_for` name precedence.
- Fix (reviewed, final): a `reload_roster_rows` flag set on reset transitions makes `apply_roster` do
  one keyed `players`-row read per carried roster player (not the whole bundle) and restore a slot's row
  only when the slot has no name, so a concurrent newer row is never overwritten; the flag is kept when a
  read fails and cleared wherever every slot is replaced anyway. Name-service is still re-asked after the
  reset, so the rename rule is intact.
- Reproduction: `src-tauri/src/pipeline_tests/name_stability.rs` — app opened during Agent Select, name
  published, OTHER's rank phase held by a long-delayed 500 so their bundle is provably stale, then presence
  flips to MENUS (dodge). Baseline publishes `name: Loading`; fix keeps the stored name.
- PR: [#6](https://github.com/opd116/opd1-trcker/pull/6), branch `fix/names-live`, final head
  `346907800a22f4cd37e1ff1c33e95076166e8efe`. Round 3 added the coverage the independent reviewer flagged:
  a second reset test for the **match end** (In Game -> Lobby; app opened mid-match) with the same stale-slot
  setup, and a **failed roster fetch after a reset** (`show_self_only`, then the retry install), which is kept
  as coverage of the retry transition and documented to pass on baseline too because `show_self_only`
  replaces every slot (the carried-row defect cannot survive that path). Baseline matrix: the dodge and
  match-end tests both fail on `0428c52` with `name: Loading` while the DB stores it; the failed-fetch test
  passes on baseline as explained. The three tests run in ~0.03 s with no wall-clock waits.
- Remaining uncertainty: verified against mocks/fixtures only; real-client observation of a dodge / match end
  with a name that appeared during Agent Select is still needed.

## Area 4 — Riot account switch (confirmed, PR #8)

**Hypothesis/area:** switching accounts in a Riot client that stays open is a supported flow; after the switch the
UI must not keep serving the previous account's data.

**Finding ACCOUNT-1 (confirmed, browser regression test fails on baseline).**
- Trigger: the Riot client switches accounts while the app is open (its session drops and reconnects; Rust replaces
  the whole live state and re-pushes My Stats when the switch is noticed). The self card's PUUID changes.
- Observed (baseline 0428c52): the UI had no reaction to the new self card, so every open, account-scoped surface
  kept the previous account's data indefinitely: the History list (rows, and the module-level `historyCache`, which
  also drew the old rows on a remount before the refresh answered; an in-flight old page could land afterwards),
  the Skins collection (including the total VP), Saved's records with/against and LAST SEEN (computed for
  `self_puuid` when `saved_players` was asked), and the profile drawer / scoreboard, whose "Your result",
  encounters and own row are relative to the previous user.
- Expected: an open page either shows the new account's data or a neutral loading state; user-relative overlays
  close rather than showing the old account's numbers.
- Root cause and source evidence: no account-change signal in the UI (`ui/src/lib/stores.ts` only stored `live`);
  refresh triggers were mount/queue switch/stage change/match end only (`HistoryList`, `Saved`, `Skins`); the
  History module cache (`ui/src/components/history/cache.ts`) was not account-scoped; in-flight guards (`gen`,
  `alive`) were only bumped by those same non-account triggers.
- Fix (reviewed; two follow-up rounds hardened it): one UI account signal in `ui/src/lib/stores.ts` —
  `selfId` prefers the live self card, then the live state's `selfPuuid` (the session's own account, which
  Rust now carries on the wire as an optional field, serialized only when known), then the last account a
  live state named, and falls back to the My Stats snapshot's puuid only before any live signal, so a stale
  snapshot cannot move the account back; `onAccountChange(fn)` fires only when two known accounts differ in
  turn (never on startup/first account, a dropped connection, an empty live state or Closed↔Menus; a
  persisted-account snapshot followed by the connected account at boot is a real change and may fire once).
  On a switch: History clears its shown page and its module cache — the cache starts an account epoch and
  rejects any page asked for under an older epoch, so an answer from a list instance the switch unmounted
  cannot repopulate it — and refreshes with the new generation; Skins bumps its generation synchronously,
  clears its collection and re-asks; Saved clears and reloads; the open tooltip, profile drawer and scoreboard
  close (`hideTip()`, then `backFromMatch({ reopenProfile: false })`) because they cannot be corrected in
  place, leaving the refreshed screen under them. Rust clears the previous session's roster slots in the same
  critical section that replaces `self_puuid`, so no old account's card can be published under the new puuid.
  The wire field keeps old payloads valid (absent when unknown, never `null`); no schema, route or dependency
  change. Round 4 closed the My Stats residual: a central `myStatsForSelf` derived store (snapshot only while
  `mystats.puuid === selfId`, preserving each consumer's tri-state meaning) is now used by every user-relative
  My Stats consumer — Competitive, NavRail rank, WaitingView, the profile drawer's Net RR/games, the recap and
  the scoreboard's "YOUR RR" — so a stale snapshot cannot draw the previous account's numbers during the
  pre-push window.
- Reproduction: `ui/tests/account-switch.spec.ts` — a fake-Tauri harness with account-aware commands; boot as
  account A, open the surface, flip the fake account and emit the new account's `live` state at the **same
  stage** (asserted, so the pre-existing stage-change refresh cannot mask the bug), then assert A's data is
  gone. Eleven cases now: History, an in-flight A page released after the switch, Skins, Saved, drawer,
  scoreboard, a scoreboard opened from the drawer whose drawer must not reopen, three "VALORANT closed,
  never-seen account, only `selfPuuid` names it" cases, and (round 4) "switch with My Stats still A's" — while
  the push is missing, Competitive is the skeleton and NavRail/WaitingView show no A numbers, and after a B
  `mystats` event they show B's. On baseline the seven mid-match cases fail with A's values (e.g. History
  expected B's row, got none; Skins expected "2,550", got "875"; Saved expected "9 games", got "3 games";
  drawer/board still open), the three closed cases fail on the fixed-before-the-wire-change sources exactly
  3/3, and the stale-My-Stats case fails on the pre-guard sources. With the final fix all eleven pass; unit
  tests pin the signal and guard semantics (13 new UI tests in total, 631 Vitest).
- PR: [#8](https://github.com/opd116/opd1-trcker/pull/8), branch `fix/account-switch-data`, final head
  `b4583967cbc0e9931eb1c7fab0cd3b2b74b7383a` (after the reviewers' follow-ups and the round-4 My Stats guard;
  both CI runs green: PR 41092685451, push 41092675595).
- Remaining uncertainty / residual: closed within the set — `collection()`'s in-flight old-account copy is
  fixed in PR #5's round-4 guard, and the stale My Stats window is guarded here. What remains is the real
  Windows + VALORANT/Riot-client validation (see the handoff).

## Area 5 — CI test flake (confirmed and fixed, PR #9)

**Hypothesis/area:** the one full local Rust run in round 1 that exited 1 with a green-looking tail, and CI
reliability generally.

**Finding FLAKE-1 (confirmed, reproduced deterministically).**
- Trigger: a `Build` push run for the docs head `271e047` failed its `checks` job in **Test Rust crates**
  (`pipeline_tests::status::matchmaking_in_the_lobby_shows_the_queue_timer_and_ends_the_recap`, `status.rs:584`,
  `assertion failed: since >= before`) while the same commit's `pull_request` run passed; the suite took 60.81 s
  instead of the usual ~13 s (two CI jobs shared the runner).
- Root cause: the test captured `before = now_ms()` **after** the tick that first records the queue timer's
  start, then asserted the later "no entry time" start (`since`, which is that earlier tick's timestamp) is
  `>= before`. That only holds while the few status reads between the tick and the capture finish inside the
  same millisecond. The app behaviour is correct — a further tick keeps the same start, which the test also
  asserts.
- Reproduction: with a 5 ms sleep simulating the loaded runner, the old test fails deterministically with the
  same assertion; the fixed test with the same sleep passes, and five consecutive runs pass.
- Fix: capture `searched_at = now_ms()` before the first `MATCHMAKING` tick and `first_seen_by = now_ms()`
  immediately after it, and assert the "no entry time" start lies inside `[searched_at, first_seen_by]` (a
  restarted timer would be outside it), plus `since <= now_ms()` and the unchanged across-ticks equality.
  A reviewer of the first version asked for exactly this stronger window. Test-only: no app code, no
  UI/dependency/schema change.
- PR: [#9](https://github.com/opd116/opd1-trcker/pull/9), branch `fix/status-queue-timer-flake`, final head
  `2fe60e67…` (after the reviewer's follow-up); CI checked on the exact head before the round report.
- Remaining uncertainty: this explains the observed CI failure and the round-1 local exit code is consistent
  with it; other real-time timing assertions (throttle/session tests with short sleeps) were not observed
  failing and were not changed.
